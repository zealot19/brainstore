1. Architecture générale

Principes directeurs
  • Standalone components — aucun NgModule, imports déclarés sur chaque composant
  • Isolation layer — tout le code custom dans src/_api/, les fichiers du template touchés au minimum
  • Lazy loading — chaque groupe de routes chargé à la demande via loadComponent()
  • Functional interceptors — pas de classes, fonctions pures injectées dans app.config.ts
  • Services providedIn: 'root' — singletons, pas de providers dans les composants
Navigateur → Angular Router → authGuard → Composant (lazy) → Service (_api/services/) → HttpClient
                                                 ↑ ↓
                                     jwtInterceptor → errorInterceptor → apiUnwrapInterceptor

3. Conventions et patterns

Pattern de page liste (tableau)

Toutes les pages de liste suivent la même structure :

Composant TypeScript
  • packages: T[] = [] — données brutes de l'API
  • filtered: T[] = [] — données filtrées affichées
  • loading = true — spinner d'attente
  • form: FormGroup — formulaire création/édition
  • editId: string | null — null = création, id = édition
  • load() — appel API + applyFilter()
  • applyFilter() — filtre local sur search
  • openCreate() / openEdit() — prépare le modal
  • submit() — create ou update selon editId
Template HTML
  • Page header + bouton principal
  • 4 stat cards style bg-{color} border-0 (pattern employee)
  • Tableau avec @for (item of filtered; track item.id)
  • Actions : d-flex align-items-center border rounded sur chaque <a>
  • Icônes : Tabler CSS (ti ti-pencil, ti ti-trash…) — pas de Feather JS
  • Modaux Bootstrap : data-bs-toggle="modal"

Icônes : règle importante

Le template utilise Feather Icons (data-feather="edit") qui nécessitent un appel JS feather.replace() après chaque rendu. Dans les boucles @for d'Angular, cet appel n'est pas déclenché automatiquement → les icônes sont invisibles.

Règle : dans tous nos composants, utiliser exclusivement les Tabler Icons CSS (<i class="ti ti-nom"></i>) qui fonctionnent sans JavaScript.

Gestion des erreurs API

Type d'erreur backendFormat reçuCe qu'affiche le composant
ApplicationError (métier) { code: "ApplicationError", message: "..." } Le message directement
Erreur DRF validation (400) { code: 400, message: "Une erreur...", details: { field: [...] } } Les details par champ : field : message
401 Unauthorized — errorInterceptor tente le refresh automatiquement
403 Forbidden — Message générique (permission refusée)

4. Intercepteurs HTTP

Déclarés dans src/app/app.config.ts dans cet ordre :

withInterceptors([jwtInterceptor, errorInterceptor, apiUnwrapInterceptor])
IntercepteurRôleDétail
jwtInterceptor Ajoute le token JWT Injecte Authorization: Bearer <access> sur toutes les requêtes vers API_BASE, sauf les URLs publiques (login, refresh, reset…)
errorInterceptor Refresh automatique Sur 401, tente un refresh via HttpBackend (bypass intercepteurs pour éviter boucle). Utilise map(res => res.data) pour désemballer manuellement la réponse refresh (non interceptée par apiUnwrap). File les requêtes en attente pendant le refresh.
apiUnwrapInterceptor Désemballe + normalise Success : extrait body.data de l'enveloppe { success, data }
Erreur : extrait le message lisible depuis error.error.message ou formate les détails de validation DRF champ par champ

Note : errorInterceptor utilise HttpBackend

L'errorInterceptor injecte HttpBackend (et non HttpClient) pour la requête de refresh, afin d'éviter la dépendance circulaire. En conséquence, cette requête bypasse tous les intercepteurs y compris apiUnwrapInterceptor. Le désemballe de la réponse refresh est donc fait manuellement : 

http.post<{ success: boolean; data: TokenPair }>(AUTH.refresh, { refresh })
  .pipe(map(res => res.data))

AuthService — méthodes principales

MéthodeEndpointDescription
login(email, password)POST /auth/login/Retourne tokens ou déclenche 2FA (requires_2fa: true). Stocke user_id temporaire pour l'étape 2FA.

logout()POST /auth/logout/Blackliste le refresh token. Nettoie TokenService et redirige vers /signin.
forgotPassword(email)POST /auth/password-reset/Déclenche l'envoi d'email (console backend en dev).
confirmReset(token, password, confirm)POST /auth/password-reset/confirm/Envoie { token, new_password, confirm_password }.
unlock(password)POST /auth/login/Revalide le mot de passe depuis l'écran de verrouillage.

authGuard — logique de navigation

Accès route protégée
    ├── isAuthenticated() → true       → Accès autorisé
    ├── getUser() → profil en cache → /lock-screen (tokens expirés mais profil connu)
    └── Aucun des deux                 → /signin?returnUrl=...

Flux 2FA

  1. Login → backend retourne { requires_2fa: true, user_id: "uuid" }
  2. AuthService stocke _pending2faUserId en mémoire et redirige vers /two-step-verification
  3. L'utilisateur saisit le code TOTP → loginWith2FA(code) envoie { user_id, code }
  4. Succès → tokens reçus, connexion complète
